# R5 — Catalog update ↔ schedule contract

## Implemented now

| Behavior | Contract |
|---|---|
| Schedule stores catalog version | Each `bounty_schedule_runs` row and slot/offer carries `catalog_version_id` used at generation / rebind |
| First schedule | **Only** via `admin_initialize_bounty_schedule` (or disposable `dev_*`). Catalog activate alone does **not** create slots |
| Later catalog publish / rollback | Existing Phase 6B2 path: rebinds **only** `scheduled` never-shown Cocktail/Ingredient offers from the new eligible pool; writes a schedule_run note `catalog_publish` / `catalog_rollback` |
| Current / exposed / grace | Prior offer + catalog binding preserved; current slot pointer may move to live catalog for Skip reserves |
| Historical scores / claims | Keep historical `catalog_version_id` / offer snapshots; never rewritten by init or publish |
| Past windows | Not regenerated by init (init refuses if any partial/complete schedule exists). Publish does not rewrite `exposed` / completed windows |
| New eligible drinks/ingredients | Become available to **future** `scheduled` slots on the next successful publish rebind (and to Skip reserves). They do **not** appear in already-exposed or past windows |

## Explicit non-assumptions

- Activating a new catalog **does not** automatically and safely rebuild an entire voyage schedule from scratch.
- Activating a new catalog **does not** create a first schedule if none exists.
- R5 does **not** add a second “regenerate future windows” Admin button beyond existing publish rebind.

## Menu-agent phase (deferred)

When the onboard menu reconstruction agent ships:

1. Agent produces a reviewed `full_snapshot`.
2. Admin stages → previews → publishes (existing).
3. Publish rebind updates remaining `scheduled` slots if pool suffices; otherwise publish fails transactionally (`REMAINING_POOL_SHORTAGE`).
4. If ops need a full future-window reshuffle beyond rebind (e.g. intentional redesign mid-cruise), that requires a **new** explicit safe operation — **not built in R5**. Flag for menu-agent / R5 follow-on:
   - Preserve exposures + claims
   - Only touch future unplayed windows
   - Idempotent request ledger
   - Refuse when finalized or when remaining pool cannot fill remaining slots

## Verification notes (R5)

- Integration proves Admin init stamps `catalog_version_id` and refuses duplicate init.
- Existing catalog publish rebind behavior was previously proven in QA-4A; R5 does not regress that contract and does not replace it.
